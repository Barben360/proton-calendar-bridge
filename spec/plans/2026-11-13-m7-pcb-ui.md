# M7 `pcb-ui` (Linux) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A desktop binary `pcb-ui` for Linux that runs the M6 daemon in-process, with a tray icon (ok, syncing, needs attention), one window (accounts, add-account wizard, per-account CalDAV switch and credentials, calendars, alerts, settings) and desktop notifications. Quitting it stops the bridge. Both `pcb` and `pcb-ui` can seal secrets with the desktop keyring (Secret Service).

**Architecture:**
- **C2 `internal/store/seal`:** an AES-GCM helper shared by `KeyFile` and a new `SecretService` sealer. The data key lives in a Secret Service item, reached through a `Keyring` interface with a pure-Go D-Bus implementation (`godbus/dbus/v5`), so `pcb` stays `CGO_ENABLED=0`.
- **C2 `internal/store` and config:** `layout.json` records the `sealer` chosen once, when the layout is created. `[secrets] backend` (`auto`, the default; `keyfile`; `secret-service`) is read only at that moment.
- **C3 `internal/service`:** `OpenHub` builds the sealer from `layout.json`. A locked keyring is `seal.ErrLocked`: the account waits and retries every 30 s, and `Status.Secrets` is `locked`.
- **`internal/ctl`, `internal/daemon`, `internal/doctor`:**
  - alert `keyring-locked`;
  - `ctl.BuildStatus`, the in-process `/v2/status` the UI reads;
  - `POST /v2/ui/show`, served only when the daemon has a `ShowUI`;
  - doctor checks secrets with the recorded sealer and warns when `pcb-ui` and the service are both installed.
- **`internal/logfile` (new):** a size-capped log file, 10 MiB × 2.
- **`internal/ui` (new, no Fyne):** `Bridge` (open config and Hub, `daemon.Run`, stop, restart, single-instance probe), the view model (`Model`, `View`, tray state, notifications to send) and the add-account `Wizard`. All of it is tested against the fake Proton.
- **`internal/ui/desktop` (new, Fyne widgets, pure Go):** the window, tray menu and dialogs, tested with Fyne's headless test driver. Platform files hold the Linux D-Bus parts: the tray-host check, notifications with a click action, autostart.
- **`cmd/pcb-ui`:** `main_linux.go` (`linux && cgo`) creates the Fyne app (GL driver, the only cgo); `main_other.go` says "not supported yet" and exits 2.

## Global Constraints

- Every rule of the M1–M6 Global Constraints still holds (`spec/plans/2026-11-12-m6-multi-account.md`):
  - the `--json` envelope and the exit codes `0`, `2`, `10`, `20`, `30`, `40`;
  - secrets never in argv, logs, errors, responses or unsealed files;
  - every `service` error is an `*exitcode.Error` with a secret-free message and a hint;
  - tests bite: the reviewer checks by sabotage, not by mutation testing;
  - live checks only on the test account, as deferred human-check steps;
  - `make lint test` is the gate;
  - `GOOS=windows go vet ./...` stays clean.
- `pcb` stays `CGO_ENABLED=0` and gains no GUI dependency. An arch test asserts that `go list -deps ./cmd/pcb` contains no `fyne.io/` package.
- Import rules (`arch_test.go`, one per new package):
  - `internal/ui` follows the `cli` rule (never `internal/proton/...`, `internal/store/...`, go-proton-api) and never imports `fyne.io/...`;
  - `internal/ui/desktop` follows the `cli` rule;
  - `internal/logfile` imports only the standard library;
  - `internal/store/seal` may import `godbus/dbus/v5`.
- Fyne's rule: a widget changes only on the main goroutine. Model events coming from daemon goroutines reach widgets through `fyne.Do`, and tests run with `-race`.
- The UI holds a secret no longer than a call:
  - the wizard's password lives in the `Wizard` until the login ends (ready or an error, not needs-captcha, since the CAPTCHA retry needs it), then is zeroed;
  - a shown CalDAV password hides again when the account pane changes or the window hides;
  - nothing secret is logged or put in a notification.
- Exact values:
  - **Log file:** `<state>/logs/pcb-ui.log`, rotated to `pcb-ui.log.1` past 10 MiB (10 × 1024 × 1024 bytes), files 0600, directory 0700.
  - **Sealer:** name `secret-service`. Its key is one Secret Service item in the default collection:
    - label `pcb sealing key`;
    - attributes `{"application": "pcb", "state": "<absolute state dir>"}`;
    - secret: 32 random bytes, content type `application/octet-stream`;
    - D-Bus session algorithm `plain`.
  - **`layout.json`:** `{"version": 2, "sealer": "keyfile" | "secret-service"}`. A missing `sealer` means `keyfile`. An unknown sealer is exit 10 with hint `upgrade pcb`.
  - **`[secrets] backend`:** `auto` picks `secret-service` when `DBUS_SESSION_BUS_ADDRESS` is set, the service answers within 2 s and the default collection is unlocked; otherwise `keyfile`. `secret-service` fails the creation (exit 10) when the keyring cannot be used. Any other value is exit 2 at config load.
  - **Locked keyring:** `seal.ErrLocked`, retry every 30 s. Alert `keyring-locked`, severity `error`, message `the desktop keyring is locked`, fix `unlock it (log in to the desktop session), pcb retries every 30 s`.
  - **Control socket:** `POST /v2/ui/show` with body `{"account": "<local-id>"}` (optional) answers `{"shown": true}`. When the daemon has no `ShowUI`, it answers a 404 envelope `unknown endpoint`.
  - **Single instance:** a second `pcb-ui` facing a `pcb-ui` sends `ui/show` and exits 0. Facing `pcb serve`, it shows the dialog, then exits 20 with the message `pcb serve (PID <pid>) already serves this state directory` and the hint `stop it (pcb service stop when installed as a service) and start pcb-ui again`.
  - **Window:** 800 × 550. The tray has three icons of our own (`ok`, `syncing`, `attention`); no Proton name or logo appears as branding.
  - **Notifications:** sent for `needs-login`, `needs-captcha`, `human-verification`, `sync-stalled` and `keyring-locked`, once per occurrence (an alert that clears and comes back notifies again). The title is the account's address; the body is the alert's message and fix.
  - **Autostart:** `$XDG_CONFIG_HOME/autostart/pcb-ui.desktop` (default `~/.config/autostart`) with `Exec=<absolute path of pcb-ui> --background`. `--background` starts in the tray only, unless no tray host answers.
  - **Install:** `make ui` builds `bin/pcb-ui`. `make install-ui` installs:
    - `$(PREFIX)/bin/pcb-ui`;
    - `$(PREFIX)/share/applications/pcb-ui.desktop`;
    - `$(PREFIX)/share/icons/hicolor/scalable/apps/pcb-ui.svg`.

## Review Focus

1. **An existing state on a desktop with an unlocked keyring:** `pcb-ui` keeps its key file, never re-seals, and Thunderbird keeps working (Task 2 `TestExistingStateKeepsItsKeyFile`).
2. **A keyring locked at start** (a user service started before the desktop login): the accounts wait with `keyring-locked`, recover by themselves once it is unlocked, make no Proton login while locked, and nothing is re-sealed (Task 2 `TestLockedKeyringWaitsAndRecovers`).
3. **A second `pcb-ui`:** the first shows its window and the second exits 0. No second `Hub.Serve` and no Proton call (Task 5 `TestSecondInstanceShowsTheFirst`).
4. **Quit during a sync pass or a 2FA wait:** the drain ends, `serve.lock` is released, `pcb.sock` is removed, and `pcb status` then says offline (Task 5 `TestQuitDrainsAndReleases`).
5. **A shown password left on screen:** switching account or hiding the window hides it. The wizard's password survives a CAPTCHA retry and is zeroed at the end (Task 7 `TestWizardKeepsPasswordForCaptchaThenZeroes`, Task 8 `TestShownPasswordHidesOnAccountChange`).

  - `dbustest.Start(t) (addr string)`: starts `dbus-daemon --session --print-address --nofork` (`t.Skip` when missing, `t.Fatal` when `CI` is set) and stops it at cleanup;
  - `sstest.Start(t) (addr string, f *Fake)`: on `dbustest.Start`, exports `org.freedesktop.secrets` and offers `f.SetLocked(bool)` and `f.Items()`.
