## E04 Calendar model events (per-calendar feed)

### Endpoints [verified in source]
- `GET /calendar/v1/{calID}/modelevents/latest` -> `{CalendarModelEventID}` (head cursor). caloxide/protonmail/calendar.go:376-390; jmdlab/internal/proton/delta.go:50-87; carbonate/internal/caldav/store.go:130-145.
- `GET /calendar/v1/{calID}/modelevents/{cursor}` -> `{CalendarModelEventID, More, Refresh, CalendarEvents:[{ID, Action, Event?}]}`. caloxide calendar.go:363-405; jmdlab delta.go:55-69; carbonate store.go:171-205.
- caloxide appends `?CalledFrom=Background` on the cursor poll (calendar.go:394). [verified] Meaning unknown ([inferred] telemetry/priority hint mirroring web client; not required).
- One feed PER CALENDAR (calendar ID in path); per-user changes live in the core loop (E05). [verified: all clients keep one cursor per calendar, e.g. jmdlab store.go:70-80 `Cursors` map calendarID->cursor; caloxide poller.go:41 "One poller runs per calendar"].
- Types: `CalendarModelEventID` string; `More`, `Refresh` ints (0/1 for More; Refresh "!= 0"). [verified: caloxide calendar.go:368-373; jmdlab delta.go:64-69]. Note jmdlab compares `More != 1` (delta.go:136), caloxide/carbonate `More == 0`. Equivalent if values are only 0/1; unverified for other values.
- Envelope also has `Code` (1000) as for all Proton responses [verified: caloxide `resp` embed].

### Payload per change [verified + claim]
- Entry = `{ID, Action, Event}`. Action: 0=delete, 1=create, 2=update (EventAction iota: caloxide events.go:39-46; same enum as go-proton-api G/event.go:93-98, which also has 3=UpdateFlags, mail only). [verified: caloxide poller.go:152-169; jmdlab delta.go:28-30]
- Whether the row is included: jmdlab claims (citing WebClients reading, secondhand, delta.go:21-26) the create/update `Event` is "without blob" (metadata only, NO encrypted cards); caloxide comment says the same (calendar.go:351-361, 391); both RE-GET the full row by ID (`GET /calendar/v1/{cal}/events/{id}`) before decrypting (jmdlab delta.go:147; caloxide poller.go:157). Delete entries carry no Event. [doc/claim: those comments; consistent with both clients, but no fixture of a real response in any repo -> unverified shape of `Event`]
- carbonate IGNORES Action: looks every ID up in current state (present=changed, absent=removed). Rationale "no assumption about action codes" (store.go:171-180; docs/ARCHITECTURE.md:176-190). jmdlab handles the create-then-delete race the same way: Action 1/2 + row GET 404 => treat as delete (delta.go:147-153). [verified] Recommendation [inferred]: M2 should do the same (ID-driven re-fetch; Action only as a hint).
- Same ID can appear several times in a sweep; jmdlab consolidates last-action-wins preserving first-appearance order (delta.go:123-128).

### Cursor semantics
- `latest` returns the current head ID, not a consumed position. [verified]
- Polling FROM `latest` with nothing changed returns no events and the same cursor (carbonate store.go:150-168, ARCHITECTURE.md:176-190, "measured against a live account"). jmdlab relies on the same: cursor unchanged => 0 decryptions, and treats `res.CalendarModelEventID == cursor` as end (delta.go:131-134).
- Important pitfall (carbonate, "measured", docs/ARCHITECTURE.md:176-190): the cursor RETURNED by reading the loop at `latest` sits past changes not yet issued; adopting it as the next cursor LOST events (two events created after, only the later reported). Fix: persist `latest` itself as baseline; after a poll that returns events, store the returned `CalendarModelEventID`. [doc/claim: carbonate; only one source, contradicts nothing, jmdlab/caloxide store `latest` as baseline too (jmdlab poller.go:218-224, caloxide poller.go:42)]. [inferred] Safe rule for M2: baseline = `latest` fetched BEFORE the full listing (jmdlab does precisely this, poller.go:206-224); replays of changes made during the listing are harmless if upserts are idempotent.
- Lag: `latest`/feed lags a write by "a second or two" (carbonate ARCHITECTURE.md:196-205, cache.go:77-82 claim). So after our own write the feed may not yet show it; M2 should write-through the cache and tolerate later replays. [doc/claim]
- Paging: loop while `More` != 0, follow returned cursor, fetch immediately (caloxide poller.go:72-111; jmdlab delta.go:108-139 with cap 1000 pages => treat as refresh; carbonate caps 20 pages => full re-read, store.go:171-205, 224).
- Refresh: `Refresh != 0` => client must discard cache and full re-sync (caloxide poller.go:94-100, jmdlab delta.go:119-122, carbonate store.go:195-199). caloxide re-seeds the cursor to the returned `CalendarModelEventID`; jmdlab returns it as NewCursor but then re-baselines from `latest` after the full listing. Refresh bit values not distinguished anywhere for calendar loop.
- Cursor too old: no source documents the actual server response. Options seen: (a) `Refresh` set [claim only: caloxide calendar.go:365 "cursor too old / state is inconsistent", jmdlab delta.go:21-23 "cursor lost server side, too far behind"]; (b) HTTP error: carbonate treats ANY error from the cursor GET as "unusable cursor => read everything" (store.go:195-200: "away longer than Proton remembers"). jmdlab/caloxide treat an error as transient failure with backoff, so a permanently invalid cursor would stall in them. [verified code; server behaviour UNVERIFIED -> live run]. Retention window unknown.
- Failure policy to copy [inferred]: error on cursor GET => log, after N failures or a 4xx (not 429/5xx) fall back to full re-list.

### Poll cadence [verified]
- caloxide: 30 s per calendar (poller.go:13-17, README:29), exponential backoff to 10 min (poller.go:24-27), alert after 3 failures, standby mode slows to 15 min after idle (caldav/standby.go:26-28), push-relaxed 5 min (poller.go:22). Claims "Proton's web client polls on a similar cadence" (poller.go:13-16; unverified).
- jmdlab: 60 s default, `poll_interval` config (poller.go:67-70, config.go:73) ONE cycle per interval for ALL calendars (calendar list + per-calendar delta request); safety full resync every 6 h (poller.go:28) plus the full at boot; /healthz stale after 5 min.
- carbonate: not a poller; calls `latest` on each CalDAV ctag read (cheap, "a client polling every few seconds costs almost nothing", ARCHITECTURE.md:93-100), cache invalidated on token change.
- cheeseandcereal_proton-cal, SevenOfNine-labs_proton-calendar-bridge: do not use the feed (grep modelevents = 0; SevenOfNine is a stub using go-proton-api read methods).

### Push / stream [doc/claim, dormant]
- "Ping-o-matic" SSE: `GET /event-notifier/v1/events` (text/event-stream); events Hello `{"id":connID}`, Ping `{"type":"calendar","identifier":"<calendar id | user id>"}`, Goodbye, Error; subscribe via `POST /event-notifier/v1/connection/{id}/loops` body `{"Add":[{"Type","Identifier"}],"Remove":[]}` (caloxide/protonmail/notifier.go:19-64; author states protocol taken from WebClients, secondhand).
- Status (author-tested 2026-10-29): route answers 404 "Path not found" with and without credentials, Unleash flag `PingOMatic` absent from the account's flags; only mail app uses it (FORK.md:112-135, README:55-60, notifier.go:25-29). Client retries every 6 h. [doc/claim: not independently verifiable; re-check live]
- Ping is only a "poll now" hint; polling stays the source of truth. M2: ignore push, poll.

## E05 Core event loop `/core/v4/events/latest` and `/core/v4/events/{id}`

### go-proton-api (G) [verified]
- `GetLatestEventID` -> `/core/v4/events/latest` (G/event.go:11-23); `GetEvent` follows `More` (Bool) up to 50 collected pages (event.go:25-56, 104-118); `NewEventStream` polls with ticker period+jitter (event.go:58-102).
- `Event` struct (G/event_types.go:10-30) has ONLY: EventID, Refresh, User, UserSettings, MailSettings, Messages, Labels, Addresses, Notifications, UsedSpace. NO Calendars / CalendarMembers / CalendarUserSettings / contacts. RefreshFlag: RefreshMail=1, RefreshAll=255 (event_types.go:77-89). Action enum 0 delete,1 create,2 update,3 updateFlags (event_types.go:91-98). Items = `{ID, Action}` + payload (EventItem, event_types.go:100-103).
- go-proton-api fake server implements core events (server/router.go:71-73, server/events.go) mail-only; no calendar anywhere in server/. Cannot be used to test calendar feeds.

### Third party [verified]
- caloxide models `Calendars []{ID,Action}` and `CalendarMembers []{ID,Action}` on the core event (caloxide/protonmail/events.go:15-56), Refresh bits `EventRefreshMail=1, EventRefreshContacts=2` (events.go:8-13). Handler: any entry in Calendars or CalendarMembers => re-list calendars (caldav/caldav.go:66-80, caldav/calendars.go:8-37). Comment: "a deleted member carries no calendar ID, so callers re-list" (events.go:20-22). Parsing is covered only by a synthetic JSON fixture the author wrote (protonmail/notifier_test.go:234-242: Action 0 delete, 1 create), not a captured response. caldav.go:66-70 comment: author was logging core events to "confirm whether Proton signals calendar deltas here" -> unconfirmed.
- Nobody models `CalendarUserSettings` in the core event (grep zero in all repos except as a GET /calendar/v1 settings response: cheeseandcereal/pkg/calendar/calendar.go:28-40 `CalendarUserSettings.DefaultCalendarID` from `GET /settings/calendar`, docs/api.md:69). Whether the core loop carries `CalendarUserSettings`, or calendar-level `CalendarSettings` changes (those probably ride the calendar model loop) is UNKNOWN from these sources.
- carbonate ARCHITECTURE.md:108-112: core `latest` moves on any mail arrival -> unsuitable as a calendar ctag. [verified claim]
- Core loop cadence: caloxide 30 s (caldav/standby.go:326-327 "coreBaseInterval matches events.pollInterval").
- Recommendation [inferred]: M2 should poll core loop only to detect calendar list/membership changes (`Calendars`, `CalendarMembers` non-empty => re-list `GET /calendar/v1` and, for new ones, bootstrap), and treat unknown extra keys as ignorable. Additionally a periodic `GET /calendar/v1` re-list (jmdlab does every 60 s cycle) is the belt-and-braces path. Core `Refresh` bit semantic for calendar: unknown; treat any nonzero Refresh as "re-list calendars + full re-sync".

## E07 What changes on edit (row fields)

### Row fields observed (JSON names) [verified in struct definitions]
- caloxide CalendarEvent (caloxide/protonmail/calendar.go:94-118): ID, CalendarID, SharedEventID, CalendarKeyPacket, CreateTime, ModifyTime, LastEditTime, StartTime, EndTime, StartTimezone, EndTimezone, FullDay, UID, IsOrganizer, RecurrenceID, Exdates, RRule, Author, Permissions, SharedKeyPacket, SharedEvents, CalendarEvents, PersonalEvents, AttendeesEvents, Attendees, Notifications.
- cheeseandcereal RawEvent (pkg/caltypes/types.go:37-80): + Color, Attendees [{Token,Status}], AttendeesInfo{MoreAttendees}; docs also list IsProtonProtonInvite, IsPersonalSingleEdit (docs/api.md:353-359; crypto.md:233-234). jmdlab adds AddressKeyPacket, AddressID (invited events; update.go:170-191).
- go-proton-api CalendarEvent (G/calendar_event_types.go:9-34) has NO ModifyTime, no IsOrganizer, RRule, RecurrenceID, Color, Notifications; cheeseandcereal states go-proton-api's calendar types are "stale (verified live)" (types.go:5-7). carbonate also notes missing Color/RecurrenceID and that `GET /calendar/v1` no longer sends top-level Name (calendar.go:75-79, ~326). -> use own structs.
- Part JSON: `{Type, Data, Signature, MemberID?, Author?}`; Type 0 clear,1 enc,2 signed,3 enc+signed (cheeseandcereal types.go:12-27; caloxide calendar.go:120-153). Sequence (SEQUENCE), DTSTAMP, UID, RRULE etc. live INSIDE the signed shared card (docs/crypto.md:175), not as a row column; so no row-level Sequence. SEQUENCE only decryptable/readable from the card (signed-only cards are clear text, no decrypt needed: type 2 data is plaintext [inferred from crypto.md:175 "plaintext + detached sig"]).
- Timestamps are unix seconds ints (jmdlab crypto.go:160 time.Unix(LastEditTime)).

### ETag candidates
- All three production-style bridges use LastEditTime: caloxide `%X%s`(LastEditTime, ID) (caldav.go:275-276, 615); jmdlab `v{schema}-{LastEditTime}` per row, FNV hash over (ID,LastEdit) of each row for a series group (caldav/backend.go:1430-1445); carbonate max(LastEditTime)+hash of IDs (caldav/backend.go:454-473). jmdlab comment (backend.go:1422-1428): "served content can change without Proton's LastEdit moving" -> an ETag schema-version constant is needed to force re-download when OUR rendering changes. [verified]
- ModifyTime: only caloxide's struct has it and uses it for ModTime in one write path (caldav.go:614); docs mention it exists on rows (crypto.md:233-234). Semantics vs LastEditTime NOT documented by any source. jmdlab comment "the max of the ModifyTime would not be enough" (backend.go:1432) is a loose naming of LastEdit. [verified: no source explains the difference] -> E07 live item.
- Group/series: edits of one occurrence create/modify a separate exception row (same UID, RecurrenceID set); master ETag must fold all rows' (ID,LastEditTime) (jmdlab, carbonate agree). Delete of master does NOT cascade (cheeseandcereal api.md:381).
- Personal part: no source records whether `LastEditTime`/`ModifyTime` moves on a notification-only change. Facts available: notifications live in the plaintext row field `Notifications` (tri-state null=inherit calendar default, []=none, array) and are re-sent on every sync update (api.md:237-248, crypto.md:209-226); there is a separate endpoint `PUT /calendar/v1/{cal}/events/{id}/personal` for personal-only updates (api.md:165); `PersonalEvents` cards (member-scoped) seen empty on live events by cheeseandcereal (api.md:250-255). Feed behaviour for a personal-only edit (does it emit Action 2 in modelevents? does LastEditTime move?) = UNKNOWN. [inferred risk] If LastEditTime does not move on a personal-only edit, an ETag based on it will miss it; the model event would still be the trigger, so M2 should key the refetch off the feed and compute the ETag from (LastEditTime, plus a hash of Notifications/Color/Attendees statuses, plus ModifyTime if present, plus render schema version).
- Also not in LastEditTime-inclusive evidence: Attendee RSVP status changes (`Attendees[].Status` plaintext) and `Color` (plaintext row column, per-event override; cannot be cleared by API, api.md:218-221). Include in the cache-validity hash [inferred].
- Sync updates are whole-object replaces (api.md:225-248): our own writes must re-send Notifications/Color/Attendees.

## Event listing `GET /calendar/v1/{cal}/events`

- Response: `{Events:[row...], More?, Total?}` + Code. Single event: `GET .../events/{id}` -> `{Event:{...}}` (cheeseandcereal wire.go:239-257; go-proton-api calendar_event.go:131-143). [verified]
- Query params: Page (0-based), PageSize, Start, End (unix), Timezone, Type (0..3), UID, MetaDataOnly (accepted, no effect per cheeseandcereal; claim). [verified code; behaviour claims by cheeseandcereal "live-verified"]
- Max PageSize: 100 (PageSize > 100 -> HTTP 400 code 2021) [doc/claim: cheeseandcereal api.md:312]. All bridges use 100 (caloxide calendar.go ListAll pageSize=100 ~l.470; jmdlab account.go:391; carbonate calendar.go:293; cheeseandcereal wire.go:18). DISAGREEMENT: go-proton-api uses maxPageSize = 150 (G/paging.go:13) - exceeds the 100 cap cheeseandcereal measured; trust 100 (150 may be stale).
- Unscoped (no Type): returns ALL rows, Page/PageSize, carries `Total` (cheeseandcereal api.md:290-312). go-proton-api `CountCalendarEvents` reads `Total` from the bare listing (calendar_event.go:9-18); caloxide uses a dedicated `GET .../events/count` -> `{Total}` (calendar.go ~479-493, comment: web client uses it for search indexing/export). carbonate stops on a short page (`len < pageSize`, calendar.go:295-315), jmdlab on short page / empty (account.go:554-588), caloxide on short page.
- With Type: windowed. Start/End honored only when Type is supplied; Type-scoped responses carry `More` (0/1) not Total; iterate Page while More==1. Types: 0 PartDayInsideWindow, 1 PartDayBeforeWindow, 2 FullDayInsideWindow, 3 FullDayBeforeWindow; query all four to see everything; max window 93 days (8035200 s; wider -> code 2000 "Time window is too big"); pad each side by 1 day; dedupe by ID; recurring masters starting before window come back under 1/3 as master rows (no server expansion) (cheeseandcereal api.md:296-339; wire.go:116-211; jmdlab account.go:395-470 same design). [doc/claim live-verified + verified code in two independent clients]
- DISAGREEMENT: caloxide's cache.go:20-25 says the endpoint "has no working time-range filter and paginates oldest-first" - it does not send Type, consistent with cheeseandcereal's "Start/End ignored without Type". Not a conflict, just that caloxide never found Type.
- `UID=` filter works server side, independent of Type, returns master+exceptions (api.md:332; jmdlab update.go:485-500).
- Cold full snapshot for M2 [inferred]: unscoped paged listing (PageSize=100, Page from 0, stop on `len<100`, or use Total / events/count) gives every row including masters, avoiding the 93-day windows; this is what caloxide and carbonate do. jmdlab/cheeseandcereal use windows because they only need a horizon. For a local cache of "all rows", unscoped is simplest and cheaper in requests. Order: caloxide says oldest-first (claim). Concurrency: caloxide pages 2-wide/3 overall (calendar.go ListWindow), jmdlab 5 concurrent slices.
- Row field value types seen: FullDay int 0/1; IsOrganizer int; RecurrenceID unix int or null; RRule string or null; Exdates []unix; Notifications null|[{Type,Trigger}]; Color string|null; Attendees [{ID?,Token,Status}] (caloxide types them loosely as interface{}). Full example JSON of a row does not exist in any repo as a fixture (jmdlab/carbonate tests use synthetic data).
- Rate limits: caloxide has a ratelimit/backoff implementation and pauses (protonmail/ratelimit_test.go; README "rate-limit pause"); 429 Retry-After handling expected.

## E09 Decrypt cost
- caloxide README.md:162-166: "decrypting 700 events takes about a second" (whole calendar; ~1.4 ms/event) while fetching 100 events/page takes "seconds per page" -> network, not CPU, dominates. caloxide/protonmail/calendar.go ListAll comment repeats "decrypting a whole calendar takes about a second". [doc/claim by author; hardware unstated, signature verification disabled in caloxide (decryptability over verification, caldav.go:154, .github/CRYPTO-FIX-PROPOSAL.md) so cost excludes verification]
- jmdlab poller comments: full snapshot cycle ~17.7 s historically for requests, delta path = 0 decryptions when cursor unchanged (poller.go:170-190; account.go:395-400 "bulk of the ~17.7 s"); i.e. cost was request count not decrypt. No per-event decrypt measurement.
- carbonate: no numbers; design principle is "one cheap request decides whether to decrypt anything" (ARCHITECTURE.md:93).
- cheeseandcereal/SevenOfNine: none. go-proton-api: none.
- Per-calendar fixed costs (not per-event): bootstrap + calendar key unlock via address keys (caloxide re-does `BootstrapCalendar` and keyring decrypt on EVERY changed batch: poller.go:139-149, wasteful; jmdlab caches keyring `calendarKeyRing`). Session-key unwrap of SharedKeyPacket/CalendarKeyPacket then SEIPD decrypt per card; signed-only cards need no decrypt.
- Verdict: no rigorous measurement exists; ~1 ms/event order of magnitude claimed once.

## Disagreements summary
1. More test: `==0` vs `!=1`. Equivalent for 0/1.
2. Max page size: 100 (live claim) vs go-proton-api 150.
3. Cursor to persist after the first walk: carbonate says store `latest` (returned cursor from polling at `latest` loses events); caloxide/jmdlab store `latest` as baseline but afterwards adopt the response's CalendarModelEventID on each poll (fine once at least one real event batch passed; carbonate's loss claim is about the first derived cursor). Not contradictory but only carbonate tested it.
4. Whether modelevents Event payload includes cards: claims say "without blob" but nobody captured a response.
5. Core loop carrying calendar changes: caloxide models them from its own synthetic fixture; its own comment says unconfirmed.
