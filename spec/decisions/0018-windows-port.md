# 0018 — Windows port: pcb-ui at login, a private named pipe, DPAPI, a native build

- **Date**: 2026-11-14
- **Decided by**: author (the run model: `pcb-ui` only, started at login, no Windows service; the control channel: a named pipe restricted to the user; the secrets: DPAPI in the user's scope; `pcb-ui` built natively on Windows with mingw-w64, not cross-compiled; the agent may use the author's Windows 11 VM), the rest the agent's calls (design `spec/designs/2026-11-14-windows-port-design.md` §5)
- **Status**: accepted, built, live check passed (step 12; `spec/experiments/W1-windows-live.md`, 2026-11-15); amends SPEC §3 (Windows leaves "only builds", a GUI on Windows leaves "not planned"), SPEC §13 ("Platforms") and decision 0015 ("Windows is next")

Both binaries run on Windows 10 (1809 or later) and 11, amd64. `pcb-ui.exe` is the bridge, started at login; `pcb.exe` talks to it or works on the files itself. They were labelled "runs, untested" (in the docs and in `pcb doctor`'s `platform` line) until the live check passed on the VM (2026-11-15); they are supported since.

- **Run model [author].** No Windows service: `pcb-ui`'s "Start at login" writes the `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` value `pcb-ui` = `"<absolute exe>" --background`, and switching it off deletes it. `pcb install` and `pcb service …` exit 20 (`no service on Windows`, hint `use pcb-ui; "Start at login" runs it at each login`). `pcb uninstall` removes the Run value only when it starts the `pcb-ui.exe` beside this `pcb.exe` on the default directories; `--delete-data` also deletes the config and state directories, DPAPI key included. `pcb serve` runs in a console.
- **Control channel [author].** `\\.\pipe\pcb-<first 16 hex of SHA-256 of the lower-cased final path of the state directory>`, with the security descriptor `O:<user SID>D:P(A;;GA;;;<user SID>)` and remote clients refused. The server refuses a client of another SID (`GetNamedPipeClientProcessId`, then its token). The client checks the pipe's **owner SID** (`GetSecurityInfo`) before it sends anything, not the server's process: a PID can be reused, and no user can make another user's SID the owner of a pipe. A pipe owned by another user, or a name already served, is refused with exit 20, like a foreign-owned socket on Linux.
- **Secrets [author].** A sealer kind `dpapi` (`"sealer": "dpapi"` in `layout.json`), the key at `<state>\secrets.key.dpapi` as `CryptProtectData` output (user scope, `CRYPTPROTECT_UI_FORBIDDEN`, an entropy string naming pcb). `[secrets] backend = auto` chooses it on Windows; `keyfile` stays; `secret-service` there is a configuration fault (exit 10). A protect failure at the first login is exit 10 (hint: sign in to Windows with the password, or `[secrets] backend = "keyfile"`). An unprotect failure is exit 20, `secrets: key-unavailable` with `secrets_cause` and a new alert `key-unavailable`, the phase kept and no logout suggested: a logon without the password (SSH with a key) cannot reach the user's DPAPI master key, and a password sign-in brings it back. Integrity failures, a blob without DPAPI's header, a machine-scope blob and a wrong size are `ErrCorrupt`. A `dpapi` state read off Windows, or a Secret Service state read on Windows, names the system it was created on (exit 10).
- **Build [author].** `pcb.exe` is cross-compiled with the others (`CGO_ENABLED=0` on every OS). `pcb-ui.exe` is built on a `windows-latest` runner in MSYS2 UCRT64 (mingw-w64 gcc, `make ui`), with `-H=windowsgui` and an icon and version resource (`make winres`, the pinned go-winres). Each release ships `pcb_windows_amd64.zip` (`pcb.exe`, `pcb-ui.exe`, `LICENSE`, `README.md`), reproducible for the same zlib and attested like the tarballs; `install.sh` refuses Windows with a pointer to the zip.
- **The agent's calls** (design §5): config in `%APPDATA%\pcb`, state in `%LOCALAPPDATA%\pcb` (`XDG_*` and `HOME` unused); every directory pcb creates has a protected DACL (the user and SYSTEM only, owner set to the user explicitly), and the checks refuse any other allowed SID than the user, SYSTEM or Administrators, naming the `icacls` fix in `pcb doctor`; file locks are `LockFileEx` on one byte at offset `1<<62`; files pcb replaces are read with `FILE_SHARE_DELETE` and replaced by a POSIX rename (`SetFileInformationByHandle`, `FileRenameInfoEx` with replace-if-exists and POSIX semantics, the target name NUL-terminated), retried for 2 s on a sharing violation; the drain is 2 s on a session end; hints quote for PowerShell; the process's zone comes from the Windows key through CLDR's `windowsZones.xml` (release 49, `internal/winzone`); `pcb-ui` checks for OpenGL 2.0 before it opens a state (exit 10, with a message box when there is no console), attaches to the parent console only to print `--version`, `--help` or a usage error, drains on `WM_ENDSESSION`, and opens the logs and `config.toml` by path through `ShellExecute`.
- **"Windows code" means code that calls Windows.** Only files that call Windows APIs carry the `windows` build tag. The logic around them (the pipe name, the DPAPI error classes, the doctor's Windows checks, the Run value's format, the foreign-sealer rule) stays untagged, so the Linux suite tests it too.

Why:
- `pcb-ui` at login covers a desktop user with no service account, no machine-scope secrets and no installer that registers a service; it is about half the work of a Windows service. A bridge running with nobody logged in is not a desktop need.
- A named pipe gets an access list and a peer check from Windows itself; an AF_UNIX socket on Windows has neither a peer check nor `chmod`, and leaves stale files.
- DPAPI keeps the key encrypted for the Windows account, with no extra library and no size limit, and the key never roams with the profile: it lives in the non-roaming state directory beside the secrets it protects.
- Fyne's supported Windows path is a native cgo build; a cross-compiled `pcb-ui` would never run in CI.

Consequences and limits:
- Supported since the live check: CI builds both binaries on Windows and runs the suites there. The live check (`spec/HUMAN-CHECKS.md` step 12, on the author's VM as a standard user) flips the label: a real logoff and logon, toasts from a zip install, Thunderbird, a second Windows user locked out of the state and the pipe, `uninstall --delete-data` (Thunderbird itself was replaced by `curl` on CalDAV and is for the author to confirm).
- Toasts from a zip install are best effort: without a Start-menu shortcut carrying the app's ID some Windows builds show none. The tray's attention state carries the same news. A click on a toast is not reported.
- A machine without OpenGL 2.0 (a VM without 3D acceleration, some remote desktops) cannot run `pcb-ui`; Mesa's software `opengl32.dll` beside `pcb-ui.exe` works around it and is not shipped.
- Stale `.key-*` temporary files at the state root (a crash while a key is created) are now removed when the Hub opens, on every system: that clean-up also runs on Linux.
- SmartScreen warns about an unknown publisher until the binaries are signed.
- New dependencies: `github.com/Microsoft/go-winio` (MIT) and `golang.org/x/sys/windows` (BSD-3-Clause, now direct), and the Unicode CLDR table (Unicode License v3), credited in `README.md`; `fyne-io/oksvg` and `srwiley/rasterx` (already in Fyne's tree) and the go-winres tool for the resource.
- Cost if wrong: the Windows files are build-tagged and the shared logic is tested on Linux, so the run model (a service later) or the secrets (Credential Manager) can change behind `internal/ctl`'s `Listen`/`Dial` and the sealer interface; a state sealed with `dpapi` would need a re-seal command that does not exist.

Next (separate projects):
1. An MSI (WiX): `pcb-ui` required, `pcb` optional (adding `pcb.exe` to the user's `PATH`), the same Run value, a Start-menu shortcut carrying the app ID (toasts), per-user (no administrator rights; to settle then).
2. Authenticode signing (SignPath Foundation or Azure Trusted Signing; not self-signed).
3. Windows on arm64.
